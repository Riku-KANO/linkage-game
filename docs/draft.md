# リンク機構歩行機械ゲーム 要件定義書

Oct 14, 2026 · @Riku KANO

## 概要とコンセプト

プレイヤーが棒・ジョイント・モーターだけで脚の機構を発明し、その機械を3Dの障害コースで歩かせるWebパズルゲーム。タイトルは「アシクミ」(脚を組む、の意)。

体験の核は次の三つ。

- クランクの回転が「歩き」に変わる瞬間を、自分の手で発見する
- 正解は一つではない。速さ・部品数・省エネのどれを狙うかで設計が分かれる
- 作った機械がガシャガシャ歩く姿そのものが報酬になる

題材は大学の機構学(四節リンク、自由度、カップラーカーブ、グラスホフの条件)。知らなくても試行錯誤で遊べ、知っていれば有利になるように設計する。

## 前提とスコープ

Webブラウザだけで完結する3Dシングルプレイゲームとし、Cloudflare Pagesで静的配信する。サーバー側の処理は持たない。

| 区分 | 内容 |
| --- | --- |
| 対象 | 平面リンク機構の設計、3D地形上での歩行シミュレーション、ステージ攻略、設計の保存と共有 |
| 対象外 | マルチプレイ、ランキングサーバー、アカウント、課金、ネイティブアプリ |
| 素材 | 機械の外装・地形・小物はBlenderで制作し、glTFで読み込む |

機構は平面(2D)で設計し、奥行き方向に位相をずらして複製することで3Dの歩行機械にする。立体リンク(球面機構など)は扱わない。この割り切りで、ソルバーとUIを大幅に単純にできる。

## ターゲットと体験目標

主なターゲットは工学系の学生、エンジニア、ものづくり好き。副次的に、Poly BridgeやZachtronics作品のような「組み立てて最適化する」ゲームの愛好者を狙う。

| 体験目標 | 測り方 |
| --- | --- |
| 機構学を知らなくても最初の歩行に到達できる | 初見のプレイヤーが、チュートリアル開始から10分以内に平地を歩かせる |
| 知識が攻略に効く | グラスホフの条件や軌道の形を意識した設計ほど高スコアが出る |
| 有名な機構を「発見」できる | チェビシェフリンクやヤンセンリンクに相当する機構を、ヒントなしで組める人が出る |
| 作った機械を見せたくなる | 設計を共有リンクで送れ、試走の様子を眺めるだけで楽しい |

## 機能要件:機構エディタ

エディタは2Dの平面作図で、編集した瞬間に機構が動いて脚先軌道が見えることを最優先にする。

| ID | 要件 | 詳細 |
| --- | --- | --- |
| E-01 | 部品 | リンク(長さ可変の剛体棒)、ピンジョイント、固定点(フレーム)、クランク(モーター駆動の回転入力)。拡張でスライダ、ギア、ばね |
| E-02 | 平面作図 | 2Dの設計ビューでリンクを置き、端点同士をつないでジョイントにする。グリッドスナップと長さの数値入力 |
| E-03 | リアルタイム軌道表示 | 編集中も機構を動かし、脚先の軌道(カップラーカーブ)を線で描く。クランクを手で回すスライダも置く |
| E-04 | 自由度表示 | グリューブラーの式で自由度を計算して表示する。0は動かない、1は正常、2以上はぐらつく |
| E-05 | 不正状態の警告 | リンクが届かない位置(組立不能)、死点、クランクが一回転できない構成を赤で示す。グラスホフの条件の判定結果も出す |
| E-06 | 脚列の複製 | 設計した脚を奥行き方向にn組複製し、組ごとのクランク位相差を設定する(例:左右3組ずつ、120°ずらし) |
| E-07 | コストと重量 | 部品ごとのコストと重量を集計して表示する。ステージの予算制約に使う |
| E-08 | 編集操作 | 元に戻す、やり直し、範囲選択、コピー、左右反転 |
| E-09 | 機体の外装 | 胴体の形と荷台をプリセットから選ぶ。重心位置が変わり、歩行に影響する |

## 機能要件:シミュレーション

機構の動きは運動学で正確に解き、機体全体の歩行は接触計算で扱う二段構えにする。リンク機構を物理エンジンの関節でそのまま組むと、拘束が発散しやすいためである。

| ID | 要件 | 詳細 |
| --- | --- | --- |
| S-01 | 運動学ソルバー | クランク角を入力として、全ジョイントの位置を求める。二つのリンクの交点で決まるジョイントは解析解で、それ以外はニュートン法で拘束を解く |
| S-02 | 組立モードの連続性 | 交点の解が二つある場合は前フレームに近い方を選び、脚がいきなり裏返らないようにする |
| S-03 | 歩行の動力学 | 機体を一つの剛体として地形の上に置く。脚先を接触点として扱い、地面との接触力と摩擦から推進と転倒を計算する。脚先の位置は運動学ソルバーの結果を使う |
| S-04 | モーターのトルク上限 | 必要なトルクが上限を超えるとクランクが止まる。速さと登坂力のトレードオフを生む |
| S-05 | 決定論性 | 固定タイムステップで計算し、同じ設計と同じステージなら同じ結果になる。共有した設計のスコアを再現するため |
| S-06 | 時間操作 | 再生、一時停止、スロー、早送り、リセット |
| S-07 | 可視化 | 脚先軌道、接地している区間、重心の投影点、クランクにかかるトルクを重ねて表示できる |

## 機能要件:ステージ・評価・進行

ステージは5章構成とし、章ごとに機構学の考え方を一つずつ学ぶ。部品は章をクリアするたびに解放する。

| 章 | 課題 | 学ぶこと | 解放する部品 |
| --- | --- | --- | --- |
| 1 はじめの一歩 | 平地を指定の距離だけ進む | 四節リンク、クランクが一回転する条件 | リンク、ピン、固定点、クランク |
| 2 段差を越える | 段差や溝を越える | 脚先軌道の高さと形、自由度 | 脚列の複製 |
| 3 でこぼこ道 | 凸凹や坂を転ばずに進む | 接地区間を平らにする軌道、重心 | 外装プリセット |
| 4 荷物を運ぶ | 重い荷物を載せて登坂する | トルクと速度のトレードオフ | ギア(減速比) |
| 5 総合 | 予算つきの複合コース | ここまでの総合 | スライダ、ばね |

評価は「クリア条件」と「スコア」に分ける。

- クリア条件:制限時間内にゴールへ到達し、転倒しない。予算のあるステージでは予算内に収める
- スコア:到達時間、部品数、コスト、消費エネルギー(トルク×回転角の積算)の4軸
- 各軸に作者が決めた基準値を置き、金・銀・銅のメダルを出す。サーバーがないため、他プレイヤーとの比較分布はMVPでは出さない

ステージとは別に、地形と目標を自由に組めるサンドボックスを用意する。

## 機能要件:保存・共有・UI

共有はサーバーを使わず、設計データをURLに埋め込んで実現する。

| ID | 要件 | 詳細 |
| --- | --- | --- |
| U-01 | 自動保存 | 設計中の機構とクリア状況を、ブラウザのlocalStorageに自動保存する |
| U-02 | リンク共有 | 設計をJSONにして圧縮し、URLのフラグメントに埋め込む。リンクを開けば同じ機械を再生でき、送り主のスコアやゴーストとも競える |
| U-03 | 書き出し・読み込み | 設計をJSONファイルとして書き出し、読み込める |
| U-04 | 二つのビュー | 機構を作る2Dの設計ビューと、歩かせる3Dの試走ビュー。ワンキーで切り替え、試走中も設計ビューの縮小版を表示する |
| U-05 | チュートリアル | 章1の最初の3ステージを兼ねる。部品を一つずつ渡し、操作を一つずつ教える |
| U-06 | 機構図鑑 | 有名な機構に相当するものを組めたら図鑑に登録し、名前と原理を解説する |
| U-07 | 言語 | 日本語。文言は外部ファイルにまとめ、後から英語を足せるようにする |
| U-08 | 録画 | 試走をGIFや動画で書き出す(拡張) |

## UI・演出

すべての画面を一つの3D空間「工房」の中に置き、画面の切り替えをカメラの移動で表現する。プレイヤーはロード画面やメニューの切り替わりを見ることなく、工房の中を動き回る感覚で遊ぶ。

### 設計原則

1. 画面は切り替えず、カメラを動かす:ホーム、ステージ選択、設計、試走は同じ3D空間の別の場所。遷移はカメラの移動で表現し、黒いフェードは使わない
2. 主役は機械:UIパネルは必要なときだけ出し、機械を隠さない。情報はできるだけ3D空間の中(機械の上や地面)に出す
3. 機構の動きをUIの言葉にする:メニューの開閉、ボタンの押下、数値メーターもリンクや歯車で動かし、題材とUIを一体にする
4. 触れば応える:操作への反応は100ms以内。遷移は操作から0.1秒以内に必ず動き始める
5. 二度目は短く:初回は演出をすべて見せ、2回目以降は短縮版にする。クリックかキーで常にスキップできる

### ホーム画面

ホームは夕暮れの工房のジオラマで、起動した瞬間から触れる状態にする。

- タイトルロゴ自体がリンク機構でできていて、読み込みの進行に合わせて部品が組み上がる。読み終わるとロゴのクランクが一回転し、文字が脚のように一歩踏み出す
- 中央の作業台では、プレイヤーが最後に作った機械が歩いている(初回はヤンセン型の見本機)。ドラッグで持ち上げたり、向きを変えたりできる
- メニュー項目は工房内の物体として置く。作業台が「続きから」、壁のコース模型が「ステージ選択」、棚が「機構図鑑」、窓の外の荒野が「サンドボックス」、工具箱が「設定」
- 物体にマウスを乗せると輪郭が光り、その物体に付いた小さな機構(引き出しのリンク、模型の中の小さな機械)が動き出す。名前のラベルが空間に浮かぶ
- カメラは常にゆっくり呼吸するように揺れ、マウスの位置に応じてわずかに視差が付く
- 工房はプレイの進行で育つ。クリアした章の機械が棚に並び、図鑑に登録した機構が壁に飾られる
- 3Dを操作しなくても使えるよう、画面の端に同じ項目のテキストメニューを置き、キーボードでも選べるようにする

### 各画面の演出

- ステージ選択:コース模型にカメラが寄ると、章ごとの台地のジオラマになる。自分の機械が模型の上を次のステージまで歩いて移動する
- 設計ビュー:作業台の製図用紙に向かってカメラが真上へ回り込み、透視投影から平行投影へ連続的に変わって2Dの図面になる。3Dと2Dが同じ空間だと直感で分かる、最も重要な遷移
- 試走:カメラはばね付きで機械を追う。前回の試走を半透明のゴーストとして並走させ、改良の効果がその場で分かる。転倒の瞬間は自動でスローになる
- 結果:ゴールするとカメラが機械の周りを回り込み、スコア4軸は歯車式のメーターが回って止まる。メダルはプレス機で刻印される。失敗時は転倒の瞬間を再生し、原因(トルク不足、重心が高い など)を一言で示して、ワンクリックで設計に戻れる

### マイクロインタラクション

- 部品をジョイントに近づけると吸い寄せられ、はまる瞬間に小さく揺れて「カチッ」と鳴る
- 自由度が1になった瞬間、機構が一度だけ試しに動いて「動く」ことを知らせる
- 組立不能や死点では、問題のリンクが赤く小刻みに震える
- ボタンは押すとリンクで沈み込み、離すと戻る。効果音はすべて金属と木の機械音で統一する

### 演出の非機能要件

| 区分 | 目標 |
| --- | --- |
| 遷移中のフレームレート | 遷移中も60fpsを保つ |
| 読み込みの隠し方 | 次の画面に必要なアセットは、カメラ移動の裏で先に読み込む。遷移が読み込み待ちで止まらない |
| 動きの軽減 | OSの「視差効果を減らす」設定(prefers-reduced-motion)を検知したら、カメラ移動を0.3秒のフェードに置き換える |
| 低性能モード | 影、被写界深度、ブルームを切り、ホームの揺れを止める。初回起動時にGPU性能を測って自動で選ぶ |
| 動きの一貫性 | イージングと遷移時間をデザイントークンとして一か所で定義し、全画面で共有する |

## 非機能要件

数値はすべて目標値で、プロトタイプの計測結果を見て見直す。

| 区分 | 目標 |
| --- | --- |
| 対応ブラウザ | デスクトップ版のChrome、Edge、Firefox、Safariの最新版。WebGL2必須 |
| 入力 | マウスとキーボード。タッチ操作は拡張で対応 |
| 描画性能 | 内蔵GPUのノートPCで60fps |
| 機構の規模 | 複製後のジョイント数が100でも、運動学ソルバーが1フレームあたり4ms以内 |
| 初回ロード | 転送量15MB以下。一般的な回線で5秒以内にタイトル画面 |
| 決定論性 | 同じブラウザでは試走結果が完全に一致する。ブラウザ間の微小な差は許容する |
| データ互換 | 設計データにバージョン番号を持たせ、古い共有リンクも読めるようにする |

## 技術構成案

静的ファイルだけで動くTypeScript構成とし、計算の中心となる運動学ソルバーは自前で実装する。

| 層 | 採用 | 理由 |
| --- | --- | --- |
| 言語・ビルド | TypeScript、Vite | 静的配信と相性がよく、ビルドが速い |
| 3D描画 | Three.js | 情報が多く、glTFの読み込みが容易 |
| UIと3Dの統合 | React、React Three Fiber、drei | 3DシーンとUIパネルを同じ状態管理の下に置き、画面遷移を状態として書ける |
| カメラ遷移・アニメーション | 自前のばね補間とイージングのデザイントークン。透視投影と平行投影の補間も自前で実装する | 全遷移の動きを一か所で調整でき、途中からの割り込みやスキップにも自然に対応できる |
| ポストエフェクト | pmndrs/postprocessing(被写界深度、ブルーム、輪郭線) | ホームの空気感とホバー時の輪郭表示に使う。低性能モードでは切る |
| 運動学ソルバー | 自前実装(TypeScript) | 規模が小さく、組立モードの扱いなど独自の要件が多い。重くなったらRustからWASMに移す |
| 歩行の動力学 | 自前の接触モデル。地形との衝突判定にRapier(WASM) | 脚先の接触力を自分で制御でき、決定論性も保ちやすい |
| 効果音 | Web Audio API | 機械音を部品の動きに合わせて鳴らす |
| 素材 | Blender → glTF(GLB) | 工房、外装、地形、小物 |
| 保存・共有 | localStorage、lz-string | サーバーが不要 |
| 配信 | Cloudflare Pages | 静的ファイルのみ |
| テスト | Vitest | チェビシェフリンクなど既知の機構の軌道を数値で検証する |

## MVPスコープとマイルストーン

MVPは「章1と章2を遊べて、作った機械をリンクで共有できる」状態とする。

- 含める:E-01(リンク、ピン、固定点、クランクのみ)、E-02〜E-08、S-01〜S-07、章1・2(計10ステージ程度)、U-01〜U-05、ホーム画面と遷移T-00〜T-08(図鑑の中身を除く)、UI・演出の非機能要件を含む非機能要件すべて
- 含めない:スライダ、ギア、ばね、E-09(外装)、章3〜5、サンドボックス、U-06〜U-08

マイルストーンと完了条件は次のとおり。

1. プロトタイプ:運動学ソルバーと2Dの設計ビューだけを作る。チェビシェフリンクとヤンセンリンクを組み、脚先軌道が既知の形になれば完了。あわせて「クランクを回して軌道を眺めるだけで楽しいか」を確かめる
2. 歩行:3Dの試走ビューと動力学を加える。ヤンセン型の機械が平地を転ばずに歩けば完了
3. ゲーム化:章1・2、評価、保存、共有、ホーム画面と画面遷移を実装する。初見の人が10分以内に最初の歩行に成功すれば完了
4. 公開:Cloudflare Pagesで公開する。遊んだ人の反応を見て、章3以降の優先度を決める

## 決定事項と残るリスク

検討中だった論点はすべて下表のとおり決定した。残る最大のリスクは、歩行の接触計算がさまざまな機構で安定するかどうかで、マイルストーン2でヤンセン型、チェビシェフ型、不格好な自作機構の3種を使って検証する。

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 動力学の方式 | 自前の接触モデルを採用する(脚先ごとに、ばね・ダンパーによる法線力とクーロン摩擦)。Rapierは地形との衝突判定だけに使い、関節機能は使わない | 機構の動きは運動学で解けているので、物理エンジンに拘束を解かせる必要がない。発散と非決定性の原因を減らせる |
| 接触の安定性 | 物理計算は240Hz固定(描画1フレームあたり4サブステップ)。クランクの回転数は最大120rpm | 速く動く脚先のめり込みと跳ねを抑える |
| 白紙から設計する難しさ | 章1は壊れた機械を直す課題から始める。全ステージに3段階のヒント(方針の一言、部品配置の影、完成形の一部)を用意する | 最初の一手で迷わせない |
| 自由度が2以上の機構 | ばねを解放する章5までは試走前にエラーにする。解放後は、ばねで拘束した自由度2までを許す | 序盤は機構の基本に集中させる |
| スコアの比較 | ランキングは作らない。共有リンクにスコアを埋め込み、受け取った人は相手の機械をゴーストとして並走させて競える | サーバーなしのまま、友人同士の比較と対戦の感覚を出せる |
| 名称と権利 | 「ストランドビースト」はテオ・ヤンセン氏の作品名なので使わず、機構名「ヤンセンリンク」で解説する | 作品名の無断使用を避ける |
| タイトル | 「アシクミ」(脚を組む、の意) | 題材とプレイヤーの行為を一語で表す |
| UIの構成 | React と React Three Fiber で、3DシーンとUIパネルを同じ状態管理の下に置く | 画面遷移を状態として書け、カメラ遷移とUIの出入りを同期させやすい |
